# Инструкции по тестированию веб-приложений

Этот документ фиксирует мой рабочий регламент для тестирования веб-приложений в этом проекте. Дальше я должен опираться на него при подготовке декомпозиции, тест-дизайна, чек-листов и баг-репортов.

## 1. Общие принципы

1. Исходить из требований как из основного источника истины.
2. Если фактическое поведение расходится с требованиями, считать это дефектом, а не новой нормой.
3. Не пересказывать интерфейс крупными блоками. Декомпозировать до атомарных, проверяемых сущностей.
4. Не упрощать артефакты "по смыслу", если из-за этого теряются состояния, ограничения, визуальные детали или трассируемость.
5. Не менять без необходимости формат артефактов, терминологию, целевое окружение и принципы нумерации.

## 2. Правила декомпозиции

### 2.1. Для верстки

1. Одна строка декомпозиции должна описывать одну проверяемую сущность.
2. Нужно отдельно выделять:
   - отдельные экраны и шаги;
   - отдельные блоки внутри экрана;
   - текстовые элементы;
   - кнопки, поля, переключатели, чекбоксы;
   - состояния элементов, если они визуально различаются.
3. Не объединять в одну строку разные состояния, если их можно проверять отдельно, например:
   - `month` и `year`;
   - `selected` и `unselected`;
   - разные шаги формы.
4. Финальные экраны, модальные окна и сообщения декомпозировать полностью:
   - иконка;
   - заголовок;
   - основной текст;
   - важные визуальные характеристики и выравнивание.
5. Формулировки должны сохранять проверяемые детали: цвет, положение, иерархию, наличие разделителей, подписи, состояние элементов.

### 2.2. Для логики

1. Декомпозировать не только сущности, но и их состояния.
2. Для выбора тарифов, опций, переключателей и шагов формы всегда фиксировать:
   - состояние по умолчанию;
   - допустимые состояния;
   - недопустимые состояния;
   - состояние "ничего не выбрано", если оно возможно или запрещено.
3. Для опций и дополнительных настроек фиксировать не только их названия, но и их влияние на систему:
   - изменение цены;
   - изменение доступности перехода;
   - изменение содержания итогового блока.
4. Использовать единые доменные названия во всех листах и артефактах. Перед сдачей отдельно сверять терминологию.

## 3. Правила тест-дизайна

1. Перед заполнением тест-дизайна составлять таблицу состояний или комбинаций.
2. Для комбинаций тарифов, типов оплаты и опций обязательно покрывать:
   - базовое состояние без дополнительных опций;
   - каждую одиночную опцию;
   - значимые комбинации из двух опций;
   - комбинацию всех опций;
   - различия между месячной и годовой оплатой.
3. Для полей ввода обязательно покрывать:
   - валидные граничные значения;
   - невалидные граничные значения;
   - пустое значение;
   - классы эквивалентности по составу символов;
   - специальные форматы, если они допустимы требованиями.
4. Каждый тест-кейс или строка тест-дизайна должен иметь ID.
5. Перед завершением нужно отдельно проверять:
   - нет ли пропусков в нумерации;
   - нет ли пустых ID;
   - не съехали ли строки после вставок или удалений.

## 4. Правила для чек-листов

1. Чек-лист должен напрямую следовать из декомпозиции и тест-дизайна.
2. Формулировки проверок должны быть точными и проверяемыми, без лишнего пересказа.
3. Если проверка завершилась с результатом `Failed`, она должна быть связана с корректным баг-репортом.
4. Если проверка относится к конкретному дефекту, нужно отдельно проверить:
   - что указан правильный ID бага;
   - что баг действительно описывает именно это расхождение;
   - что проверка и баг не противоречат друг другу по ожидаемому результату.
5. Перед сдачей проверять чек-лист на структурную целостность:
   - нет ли случайных сдвигов строк;
   - нет ли пропущенных разделителей, если они используются как часть структуры;
   - нет ли строк с неполным заполнением обязательных колонок.

## 5. Правила для баг-репортов

1. Баг должен описывать расхождение между ожидаемым поведением по требованиям и фактическим поведением.
2. Нельзя формулировать баг только по наблюдаемому результату без сверки с требованиями.
3. Для каждого бага обязательно фиксировать:
   - краткий и однозначный заголовок;
   - приоритет или серьезность;
   - статус;
   - предусловия;
   - шаги воспроизведения;
   - ожидаемый результат;
   - фактический результат;
   - окружение.
4. Если одна `Failed` проверка указывает на отдельное расхождение, нужно убедиться, что под нее действительно создан баг.
5. Перед сдачей выполнять отдельную проверку полноты баг-репортов:
   - все найденные дефекты заведены;
   - нет пропущенных багов;
   - нет багов с перевернутой логикой ожидаемого и фактического результата.

## 6. Правила по окружению

1. Окружение фиксировать единообразно во всех артефактах.
2. Не подменять целевое окружение своим рабочим окружением без явной причины.
3. Если тест проведен в ином окружении, это нужно явно отметить, а не смешивать с целевым.
4. Перед сдачей сверять окружение в чек-листах и баг-репортах с заданными требованиями.

## 7. Обязательные проверки перед сдачей

Перед завершением задачи я обязан отдельно пройти этот контрольный список:

1. Проверил ли я все спорные места против требований, а не только против UI.
2. Декомпозированы ли сущности атомарно, без укрупненного пересказа.
3. Разделены ли все значимые состояния, включая `month/year`, selected/unselected, пустые и запрещенные состояния.
4. Зафиксировано ли влияние каждой логической сущности на итоговое поведение системы.
5. Есть ли ID у всех строк тест-дизайна и нет ли пропусков в нумерации.
6. Все ли `Failed` проверки ссылаются на существующие и корректные баг-репорты.
7. Все ли найденные дефекты действительно заведены отдельными багами.
8. Совпадает ли терминология во всех артефактах.
9. Совпадает ли окружение во всех артефактах с требуемым.
10. Нет ли технических ошибок оформления: опечаток, структурных сдвигов, пустых обязательных ячеек, некорректных ссылок на баги.

## 8. Приоритет при нехватке времени

Если времени мало, нельзя жертвовать следующими вещами:

1. Сверкой с требованиями.
2. Атомарностью декомпозиции.
3. Полнотой состояний и граничных значений.
4. Трассируемостью между проверками и багами.
5. Корректностью ожидаемого результата в баг-репортах.
